# DECISIONS

実装中に決めたことの記録。新しいものを下に追記する。

## D-001: TypeScript はビルドせず `--experimental-strip-types` で直接実行

**日付**: 2026-09-20 / **Step**: 1

Node v24（開発機・サーバーとも）が型注釈の除去をネイティブに扱えるため、tsc でのビルド工程を置かない。
`tsc --noEmit` は型チェック専用として残す。

- 利点: ビルド成果物とソースの二重管理がなくなり、デプロイが「git pull して再起動」で済む
- 代償: Node 22 未満では動かない。`engines` で >=22 を宣言済み
- 再検討の契機: デコレータなど型除去だけでは扱えない構文が必要になったとき

## D-002: `createApp()` でアプリ生成とサーバー起動を分離

**日付**: 2026-09-20 / **Step**: 1

`src/app.ts` がアプリを返し、`src/server.ts` がそれを listen する。
テストは `createApp().request(...)` でポートを開かずに検証でき、テストの並列実行でポート衝突が起きない。

## D-003: 会話ログの保存は後続タスクとして保留

**日付**: 2026-09-20 / **Step**: 1

本プロジェクトの設計プロセス（プロンプトのやり取り）を後から振り返れるよう保存したい、という要望。
アプリの機能ではなくリポジトリの資産として扱う。MVP（Step 9）完了後、または区切りの良いタイミングで着手する。

- 想定: `docs/journal/` に設計判断の経緯を残す、もしくはセッションログのエクスポートを置く
- 保留の理由: MVP の実装を優先するため。急ぎではないとの確認済み

## D-004: 時刻はすべて UNIX epoch ミリ秒の INTEGER

**日付**: 2026-09-20 / **Step**: 2

SQLite に日時型はない。文字列で持つと比較（期限切れ判定）とタイムゾーンで事故るため、
全テーブルで epoch ミリ秒の INTEGER に統一する。表示時のみアプリ側で JST に整形する。

## D-005: 削除は論理削除、監査ログはDBトリガーで追記専用を強制

**日付**: 2026-09-20 / **Step**: 2

SPEC §2.7 で「削除されたお知らせの本文も監査ログから追跡できること」が要件のため、
notices は `deleted_at` による論理削除とし行を物理削除しない。

監査ログの改竄防止はアプリ層の規律だけに頼らず、`audit_logs` に BEFORE UPDATE / BEFORE DELETE
トリガーを置いて DB レベルで拒否する。アプリのバグや手動操作でも消えない。

- 代償: 運用で本当にログを消す必要が出たらトリガーを一時的に外す手間がかかる。保持90日の要件からは許容

## D-006: settings は KVS 形式（1項目1行）

**日付**: 2026-09-20 / **Step**: 2

設定項目は数個で、追加のたびに ALTER TABLE したくない。key-value の1行1項目とし、
値は JSON テキストで保存してアプリ側で型付けする。

壊れた値・型違い・未知のキーは既定値に倒す。**設定が壊れても掲示板は動き続ける**のが狙い
（SPEC §2.4 のオフライン耐性と同じ思想）。

## D-007: 掲示板の読み取りクエリに部分索引を張る

**日付**: 2026-09-20 / **Step**: 2

掲示板は「今生きているお知らせ」を繰り返し引く。
`idx_notices_active` を `WHERE deleted_at IS NULL` の部分索引にし、削除済みを索引から外す。

## D-008: 掲示板画面はビルド工程なしの素の HTML/CSS/JS

**日付**: 2026-09-20 / **Step**: 3

対象が Safari 16 (iPad Pro 9.7 / A9X) 固定。バンドラを挟むと transpile ターゲットの調整が
必要になるうえ、壊れたときの原因追跡が増える。`public/` をそのまま配信する。

- アニメーションは `transform: translate3d` のみ。GPU 合成に乗せ、A9X でも滑らかに保つ
- `:has()` など Safari 17+ の機能は使わない
- 再描画は内容に変化があったときだけ。毎回 DOM を差し替えるとスクロールが先頭に戻ってしまう

## D-009: 表示設定の既定値を実測して調整

**日付**: 2026-09-20 / **Step**: 3

当初 fontScale 22（= 22vh）としたが、実際に描画すると 169px となり画面に2文字しか入らず、
文として読めなかった。12（約92px）に変更し、あわせて scrollSpeed を 120→220 px/秒に上げた
（文字が大きいほど一周に時間がかかるため）。

**教訓**: 表示系の既定値は机上で決めず描画して確認する。最終的な値は実機で詰める。

## D-010: Discord アプリのアイコンは生成スクリプトで管理

**日付**: 2026-09-20 / **Step**: 4（準備）

アイコンを画像編集ツールで作ると再現・微調整ができない。`assets/make-icon.py` でドットマトリクス
（琥珀色の LED 掲示板風、文字は "EM"）を生成し、SVG をリポジトリに置く。
色・文字・ドット密度はスクリプト上部の定数で変えられる。

    python3 assets/make-icon.py > assets/app-icon.svg

**検討した案**: 掲示板の絵（小さいと潰れて判別不能）、「掲」の一文字（明快だが電光掲示板らしさが薄い）。
Discord のサーバー一覧では 48px 程度で表示されるため、小サイズでの可読性を基準に選んだ。

## D-011: Discord アプリの登録情報

**日付**: 2026-09-20 / **Step**: 4（準備）

- 名前: リビングの電光掲示板
- タグ: 掲示板 / お知らせ / シェアハウス / サイネージ / ユーティリティ
- アプリ ID は公開値なので記録して差し支えないが、**Client Secret と Bot Token は .env のみ**に置く

## D-012: ロール検証は Bot トークンで行い、失敗時は必ず拒否

**日付**: 2026-09-20 / **Step**: 4

ロールの取得に OAuth の access_token ではなく **Bot トークン**を使う
（`GET /guilds/{guild}/members/{user}`）。ユーザー側のスコープ設定に依存せず確実にロールを見るため。
OAuth に要求するスコープは `identify` のみに抑えられる。

判定は安全側に倒す。**サーバー未参加・ロールなし・API エラー・ネットワーク例外はすべて false**。
Discord に到達できないときに通してしまわないことを優先する（テストで担保）。

## D-013: セッションは署名付き Cookie、DB に持たない

**日付**: 2026-09-20 / **Step**: 4

HMAC-SHA256 で署名した Cookie にユーザーIDと表示名を載せる。住人数が少なく、
失効は有効期限（7日）で足りるためセッションストアを置かない。

ロールの再確認は Cookie の期限切れ時（＝再ログイン時）に走る。毎リクエスト Discord に
問い合わせると遅く、API 制限にも当たる。

- 代償: ロールを剥奪しても最大7日は書き込めてしまう。監査ログがあるので追跡はできる
- 署名検証は `timingSafeEqual`。長さが違う場合は事前に弾く（例外を投げるため）

## D-014: パラメータプロパティは使えない（D-001 の制約が実際に出た）

**日付**: 2026-09-20 / **Step**: 4

`constructor(private readonly x: T)` の書き方は型の除去だけでは処理できず、
`ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` で起動に失敗する。通常のフィールド宣言に書き換えること。

**注意**: `tsc --noEmit` は通ってしまうため、型チェックでは検出できない。
起動して初めて分かる。Step 9 のデプロイ前チェックに「起動確認」を入れておく。

## D-015: 書き込みは必ずサービス層を通し、操作と監査ログを同一トランザクションにする

**日付**: 2026-09-20 / **Step**: 5

監査ログの記録漏れをアプリの規律だけに頼ると、経路が増える（Web / Bot / API）につれ必ず漏れる。
`src/service/` に書き込み操作を集約し、**操作と `recordAudit()` を同じトランザクション**で実行する。
`src/repo/` を直接呼ぶとログが残らないため、ルート層から repo の書き込み関数は呼ばない。

これにより「操作は成功したがログが無い」状態が原理的に作れない。
失敗した操作でログが残らないことも、二重削除でログが増えないこともテストで担保している。

## D-016: 本文の上限は 200 文字（TBD-4 の解決）

**日付**: 2026-09-20 / **Step**: 5

DB の CHECK 制約ではなくアプリ層で検証する。エラーメッセージを日本語で返せるため。
200 文字は、既定の設定（92px・220px/秒）で一周におよそ1分かかる長さ。
これ以上は電光掲示板として読み切れない。

同時表示件数は制限しない。期限（既定24時間）で自然に絞られるため。

## D-017: 管理画面は認証を2層で守る

**日付**: 2026-09-20 / **Step**: 5

- `/api/admin/*` — `requireAuth` で 401 を返す（機械向け）
- `/admin/*` — 未ログインなら `/auth/login` へリダイレクト（人間向け）

API に 401 を返すのは管理画面の JS が再ログインへ誘導できるようにするため。
HTML を直接開いた場合に 401 の素っ気ない画面を見せないよう、ページ側はリダイレクトにしている。

## D-018: SSE では「変わった」合図だけを送り、中身は送らない

**日付**: 2026-09-20 / **Step**: 6

イベントには内容を載せず、受け取った iPad が `/api/notices` を取り直す。

- 取得経路が1つ（ポーリングと共通）になり、再接続時に内容がズレない
- SSE が使えない環境でも同じコードパスで動く
- 代償: 1往復増えるが、LAN 内なので無視できる（実測 147ms で反映）

## D-019: イベント発行はトランザクションの外

**日付**: 2026-09-20 / **Step**: 6

コミット前に通知すると、受け手が取り直したときにまだ古い内容が返る。
サービス層では `db.transaction(...)()` の戻り値を受けてから `emit` する。
操作が失敗した場合（戻り値が undefined）は発行しない。

## D-020: SSE とポーリングを併用する

**日付**: 2026-09-20 / **Step**: 6

SSE 接続中もポーリングを止めず、間隔を 30秒 → 5分 に緩めるだけにする。
SSE が「切れたことに気づかないまま死んでいる」状態（中継のタイムアウト、
iPad のスリープ明けなど）でも、最大5分で復帰できる。

- 接続断は指数バックオフ（1秒→最大30秒）で再接続し、その間はポーリングを 30秒に戻す
- 25秒ごとに ping を送り、中継のアイドルタイムアウトを避ける

## D-021: Bot のハンドラは discord.js に依存しない純粋関数にする

**日付**: 2026-09-20 / **Step**: 7

`src/bot/handlers.ts` は入力（実行者・引数）と出力（返信文面）だけを扱い、
discord.js の型を受け取らない。`src/bot/index.ts` が interaction から値を取り出して渡す。

Discord を起動せずにコマンドの中身をテストでき、実際 19 件のテストがすべて
ネットワークなしで走る。

## D-022: Bot のロール判定は interaction の情報を使う

**日付**: 2026-09-20 / **Step**: 7

Web の OAuth 経路（D-012）は Bot トークンで API を叩くが、Bot 経路では叩かない。
Discord が interaction に実行者のロールを含めて渡してくるため。

- API 呼び出しが1回減り、レート制限にも当たらない
- 判定できない形だった場合は false（安全側。D-012 と同じ方針）
- DM からの実行と、別ギルドからの実行も拒否する

## D-023: Bot の起動失敗で掲示板を止めない

**日付**: 2026-09-20 / **Step**: 7

同一プロセスだが、Bot の `startBot()` は try/catch で囲み、失敗しても Web サーバーは動かす。
掲示板の表示は住人全員が見るもので、Bot の不調に巻き込まれるべきではない
（SPEC §2.4 のオフライン耐性と同じ考え方）。

`DISABLE_BOT=1` で Bot だけ止められる。Web の動作確認時に使う。

## D-024: API キーは SHA-256 ハッシュで保存、平文は発行時のみ返す

**日付**: 2026-09-20 / **Step**: 8

DB には平文を置かない。漏れても元のキーは復元できない。

- パスワードと違い**高エントロピーな乱数**（24バイト）なので、bcrypt 等の
  ストレッチングは不要。総当たりが現実的でないため SHA-256 で足りる
- 照合は `timingSafeEqual`
- 一覧表示用に先頭9文字（`sb_` + 6文字）だけ別列に保存する
- **監査ログにも平文・ハッシュを載せない**（id・ラベル・接頭辞・所有者のみ）
- 全テーブルを走査して平文が存在しないことをテストと実機の両方で確認

## D-025: API キーはロールを失っても有効、失効は明示操作のみ

**日付**: 2026-09-20 / **Step**: 8

セッション（7日で期限切れ→ロール再確認、D-013）と違い、キーは失効させるまで有効。

住人が書いたスクリプトが、ロール構成の変更で予告なく止まるのを避けるため。
不要になったキーは管理画面から失効させる。誰のキーが使われているかは
一覧の「最終使用」と監査ログで追える。

- 代償: 退去した住人のキーが残りうる。運用で失効させる（OPERATIONS.md に記載予定）

## D-026: node の絶対パスを unit ファイルに埋め込む

**日付**: 2026-09-20 / **Step**: 9

サーバーの node は mise 管理（`~/.local/share/mise/installs/node/lts/bin/node`）。
systemd は対話シェルの PATH を引き継がないため、そのままでは `/usr/bin/node`（v18）が
使われ、`--experimental-strip-types` が無く起動に失敗する。

さらに **systemd は ExecStart の「コマンド本体」に環境変数を展開しない**。
`ExecStart=${NODE_BIN} ...` と書くと 203/EXEC になる（引数部分なら展開される）。

そのため unit に `@NODE_BIN@` というプレースホルダを置き、`setup.sh` が
実行時に検出した絶対パスで sed 置換してから配置する。

- node のバージョンが上がったら `setup.sh` を流し直す（パスが変われば unit も更新される）
- `preflight.sh` は systemd 側から見える node のバージョンも表示し、差異に気付けるようにした

## D-027: .env は systemd ではなく node に読ませる

**日付**: 2026-09-20 / **Step**: 9

`EnvironmentFile=` は使わず、`node --env-file-if-exists=.env` に任せる。

同じファイルを systemd と node の両方が解釈すると、値に `#` や引用符が入ったときに
解釈が食い違い、片方だけ壊れる。読み手を1つに絞る。

## D-028: バックアップの取得直後に健全性を確かめる

**日付**: 2026-09-20 / **Step**: 9

`VACUUM INTO` で取得し、`gzip -t` で圧縮ファイルの健全性を確認してから完了とする。
「取れているつもりで壊れていた」を、復元が必要になった当日に気付くのを避ける。

復元手順は OPERATIONS.md §4 に書いた。実際に展開して
`PRAGMA integrity_check` が ok になることを確認済み。
