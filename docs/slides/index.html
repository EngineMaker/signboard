使い方

書き込む方法を3つ用意しました

Discord /signboard post と打つだけ。たぶん普段はこれしか使わない気がします
管理画面 スマホのブラウザから開けます。過去のお知らせを消したり、文字サイズやスクロール速度を変えたりできます
API 自分のスクリプトから叩けます。ゴミ出しの日に自動で流す、みたいなことができるはず

どれで書いても同じ掲示板に出ます。誰が書いたかもちゃんと残ります

使い方

Discordから投稿してみる

# 24時間表示される（既定）
/signboard post text:土曜に共用部の大掃除やります。10時集合

# 12時間だけ表示する
/signboard post text:明日は断水します hours:12

# いま流れているものを確認する
/signboard list

放っておくと期限が来たら勝手に消えます。古いお知らせが残ったままだと、そのうち誰も読まなくなりそうだったので

使い方

誰でも書けると困るので

EM住民ロールを持ってる人だけ

Discordのロールをそのまま権限に使いました。新しい住人が入ったらロールを付けるだけで済むし、アカウントを別に作らなくていいので楽です

操作の履歴は全部残しました

投稿も編集も削除も記録しています。消したお知らせの本文も後から見られます。この履歴自体は誰も消せないようにしてあります

いたずら防止というより、「あれ誰が書いたんだっけ」を後から調べられるようにしたかった

小さいです

1プロセス

WebサーバーもDiscord Botも同じプロセスです。データはSQLiteのファイル1個だけ。ハウスのUbuntuに置いてるので支払いもゼロ

技術選定

iPadが古いので、そこから考えました

iPad Pro 9.7インチ / iPadOS 16

2016年の機種で、OSはもう上がりません。Safari 16で動かないものは使えない。メモリも2GBしかないのに24時間つけっぱなしにします

なのでフレームワークはやめました

掲示板の画面は素のHTMLとCSSとJavaScriptです。ビルドしないのでそもそも互換性で困らない。デプロイも git pull だけで済みます

サーバー側はNodeとHonoとSQLite。住人が数十人、お知らせも数十件なので、Postgresを立てるほどでもないかなと

仕組み

投稿するとすぐ画面が変わります

Discord / 管理画面 / API
        │
        ↓  書き込み
   ┌─────────┐
   │ サーバー │ ── SSE ──→ iPad「変わったよ」
   └─────────┘                  │
        ↑                        │
        └──── 取り直す ←─────────┘
147ミリ秒で反映（実測）

サーバーからは「変わったよ」という合図だけを送って、中身は送っていません。受け取ったiPadが改めて取りに行きます。取りに行く経路が1本になるので、途中で切れてもズレないはず

余談 / Server-Sent Events

SSE（Server Sent Events）というのを教えてもらいました

ブラウザ側

// EventSource は HTML 標準の API
new EventSource('/api/stream')
  .addEventListener('notices-changed', () => {
    fetchNotices();
  });

APIのエンドポイントに対してイベントリスナーを追加できます
切断してもブラウザが勝手に繋ぎ直してくれるらしい

サーバー側が流しているもの

Content-Type: text/event-stream

event: connected
data: 1789876681067

（数時間経過…）

event: notices-changed
data: 1789876712043

通信を閉じずに、ゆーっくりテキストを返してるような感じ
ただの HTTP

余談 / なぜ WebSocket ではないのか

WebSocketじゃないの？と思ったけど

手段向きこの用途での評価
ポーリング 都度リクエスト 確実だけど、30秒間隔だと最悪30秒待つことになる。ずっと表示してると気になりそう
SSE サーバー → ブラウザ これにしました。ただのHTTPなのでTunnelもそのまま通るし、再接続も最初から付いてくる
WebSocket 双方向 今回iPadから送りたいものが無い。接続の昇格が必要で、経路によっては塞がれることもあるらしい

iPadOS 16のSafariでも普通に動きました。古い端末が相手だと、枯れてることがそのまま強みになる気がします

仕組み

サーバーが止まっても画面は動かしたい

動かしてるのは普段づかいもしてるマシンで、自動更新で勝手に再起動したりします。ずっと動いてる前提は最初から捨てました

  • 取得できた内容はiPad側に保存しておいて、通信が切れても最後の内容を流し続けます
  • ただし隅に小さく「オフライン」と出します。古い情報を新鮮な顔で流すのも嫌なので
  • 繋ぎ直しは勝手にやってくれるので、サーバーが戻れば追いつきます

数分止まっても誰も困らない状態にしておけば、まあいいかなと

進め方

いきなり作らせないようにしました

01

まず質問してもらう

一度に3〜5問までにしてもらって、何往復かに分けて聞いてもらいました。答えをSPEC.mdにまとめてもらって、それでよければ次へ

02

作り方を提案してもらう

技術の選択肢を2〜3案、それぞれの良し悪し付きで。実装は9ステップに分けて、各ステップに「これができたら完了」という条件を付けてもらいました

03

1ステップずつ進めてもらう

終わるたびに条件の確認結果を報告してもらって、こっちが見てから次へ。計画から外れそうなときは止めて相談してもらうようにしました

進め方

決めたことはファイルに残してもらう

SPEC.md 何を作るか。質問に答えた内容と、サーバーを調べて分かったこと
PLAN.md どう作るか。技術を選んだ理由と、9ステップの中身と進み具合
DECISIONS.md 作りながら決めたこと28件。なぜそうしたか、代わりに何を諦めたか
OPERATIONS.md 動かし方と、壊れたときの直し方。手でやるしかない部分もここに

これがあると会話が途切れても続きからやれます。実際、途中で接続が切れたり全然違う話をしたりしたけど、ファイルを読み直してもらえば戻ってこれました

やってみて

AIが間違えたところもあります

  • 最初、文字が大きすぎて2文字しか入りませんでした。画面に描いてみて初めて気づいたやつです
  • 型チェックは通るのに起動しないことがありました。TypeScriptのある書き方が、ビルドなしだと動かないらしい
  • サーバーに置いたら古いNodeを掴んで動かなかった。手で動かすとv24なのに、サービスにするとv18になってました

どれも動かしてみないと分からないやつでした。各ステップに確認できる条件を付けておいてよかったと思います
